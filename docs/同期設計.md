## 「自分のアカウントだけ」に制限する方法（メールアドレスをコードに書かない）
Security Rules には、メールアドレスもユーザーIDも書かない。代わりに「許可された利用者の一覧」をFirebaseの画面で作る。

1. Sync-1で各端末にログインできたら、Factoryの「Googleログイン」画面に出る **ユーザーID** をコピーする
2. Firebase Console の Firestore で、`owners` というコレクションに、そのユーザーIDを名前にした空のドキュメントを1つ作る（Firebase Consoleからの書き込みはルールの対象外なので、アプリからは作れない）
3. Security Rules は「`owners/{自分のID}` が存在する人だけ、自分の場所（`users/{自分のID}`）を読み書きできる」とする

```
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function isOwner(uid) {
      return request.auth != null && request.auth.uid == uid
        && exists(/databases/$(db)/documents/owners/$(request.auth.uid));
    }
    match /owners/{id} { allow read, write: if false; }        // アプリからは読み書き不可
    match /users/{uid}/{doc=**} {
      allow read, create, update: if isOwner(uid);
      allow delete: if false;                                  // クラウドからの削除は禁止
    }
  }
}
```
- 他人がURLを知っていてGoogleでログインしても、`owners` に登録されていないので、Factoryのデータを読むことも書くこともできない
- Rules は Firebase Console に保存され、GitHubには置かない（テンプレートにも個人情報は含まない）
- Firestoreを使い始めるのは Sync-2 から。Sync-1では Firestore を作るだけで、アプリからは接続しない

## 無料枠（Sparkプラン）の扱い（Firebase公式の記載に合わせた表現）
- 支払い情報なしで使える（公式：「No payment information needed to get started or to use only the no-cost Firebase products」）
- Cloud Firestore の無料枠：保存 1GiB、読み取り 5万件／日、書き込み 2万件／日、削除 2万件／日、転送 10GiB／月。1件の最大サイズは 1MiB
- 1日ごとの無料枠は「米国太平洋時間の午前0時ごろにリセット」（公式：「Quotas are applied daily and reset around midnight Pacific time」）。日本時間では夏時間の有無で変わるため、決まった時刻は表示しない
- Sparkプランで無料枠を超えた場合、その製品（Firestore）の利用が止まる。公式の料金プランのページには「月の無料枠を超えた場合、その月の残りの期間、その製品の利用が止まる」と書かれている。**いつ再開するかは断定しない**
- 止まっている間も、Factoryは端末内のデータで今までどおり使える（同期だけが止まる）。料金は発生しない（Sparkプランには支払い情報が登録されていないため）
- Factoryの使い方では無料枠の数%程度の見込み。Sync-4 で、当日の書き込み数が目安を超えそうなときに事前に警告する

## 以降の段階の要点（承認済みの設計）
- Firestoreの構造：`users/{uid}/meta/factory`（クラウド登録済みの印）、`users/{uid}/{保存先}/{id}`（IndexedDBの1件＝1件）
- 初回同期：この端末とクラウドの状態で4通りに分ける。**空の端末からは何も送らない**。クラウドが空でこの端末にデータがある場合だけ「この端末のデータをクラウドへ登録」を表示し、押したときだけ登録（事前に自動バックアップ）
- 削除は「削除の印」で表し、利用者が実際に削除操作をしたときだけ送る。Rulesでクラウドからの削除を禁止
- 競合：rev（更新番号）で確認。違う項目は自動で合わせ、同じ項目は両方残して利用者が選ぶ。変更履歴は追加だけなので両端末分が残る
- 同期状態：同期済み／同期中／オフライン（端末に保存済み）／同期エラー＋最終同期日時を常に表示

## Sync-2 設計（2026-10-05 ユーザー承認）
### 正本
- 初回登録の前：各端末（今と同じ）
- 初回登録：**初回正本の端末は固定しない**。初回登録画面でその端末のデータを確認し、利用者が「この端末を初回正本にする」と明示的に決めた端末だけが登録できる（8プロジェクトが正しく入っている端末を正本にする）
- 初回登録の後：クラウドが共通の正本。各端末は完全なコピーを持ち、オフラインでも使える
- Sync-3完成前は、初回正本にした1台だけで編集する運用としていた。現在はSync-3実機確認済みのため、PC・iPhoneの両方で編集できる

### 初回登録の確認画面に表示するもの
- プロジェクト数／プロジェクト名の一覧（8プロジェクト）
- 仕様書数／要望数／変更履歴数／その他の同期対象件数（種類ごと）
- バックアップ成功状態（JSONファイル・端末内の控え。両方成功しないと登録ボタンは押せない）
- 個人情報らしき記述の件数（止めずに見直せる）
- 「この端末を初回正本にする」のチェック

### 初回登録の流れ
事前チェック（ログイン・owners登録・オンライン・クラウドが空・端末データの検査・1MiB超の記録の分割計画）→ 確認画面 → 自動バックアップ（ファイル＋端末内の控え）→ 送信（端末のデータは読むだけ・送信中は編集ロック・200件ずつ・各記録に指紋）→ 全件を読み直して件数と指紋を照合 → 一致したときだけ最後に「登録済みの印」（登録元端末・日時・件数・世代番号）。途中で失敗しても端末は無変更、続きから送り直せる

### 2台目以降
- クラウドが登録済みのときだけ取り込む。この端末からは送らない
- 端末にデータがある場合（iPhoneの独自データ等）：**勝手に消したり統合したりしない**。2-2の予行演習で件数と内容を表示し、利用者が判断する。切り替える場合は先にバックアップ（ファイル＋端末内の控え）
- 取り込みは「全部成功するか、何も変わらないか」。取り込み後に件数と指紋を照合

### 段階
2-0 Firestore作成・Rules・owners登録（利用者操作。Factoryのデータは送らない）→ 2-1 クラウドの状態を読むだけ → 2-2 予行演習（各端末の件数・内容を表示）→ 2-3 初回登録 → 2-4 2台目以降の取り込み

### Sync-2-1（実装済み）
- Googleログイン画面の「クラウドの状態を確認」：`users/{UID}/meta/factory` を `getDocFromServer` で1件読むだけ
- 表示：空／登録途中／登録済み（登録元・日時・世代・件数・プロジェクト名）／許可なし（owners・ユーザーIDの案内）／オフライン／接続不可。結果は端末に保存しない
- `js/sync/cloud.js` は書き込みの命令を持たない。db.js・端末の保存領域を使わない（自動テストで確認）

### Sync-2-2（実装済み）
- 「同期の予行演習」（#/sync-check）：この端末のデータを読むだけで、同期対象件数・プロジェクト名（Phase 7の順・8件がそろっているか・重複）・仕様書数・要望数・変更履歴数・その他件数と内訳・同期しないもの（端末ごとの設定・localOnly）・バックアップ可否・大きすぎるデータ（900KB超）・個人情報らしき記述・データの指紋・最後の更新を表示。結果はコピーして端末どうしで見比べられる

- 個人情報らしき記述は、メールアドレス・電話番号・住所・郵便番号・人名＋敬称・学籍番号などの具体的なものだけを数える（「生徒」「保護者」などの一般的な言葉は数えない）

### Sync-2-3（実装済み）
- 「初回正本登録」（#/sync-register）：事前チェック（ログイン・オンライン・owner・クラウドが空・Phase 7の8プロジェクト（重複なし）・バックアップ可）→ 登録する内容（件数・名前）→ バックアップ（端末内の控え＝別データベース factory-sync に保存して読み直し確認、ファイル factory-presync-YYYYMMDD-HHMM.json、保存の確認チェック）→「この端末を初回正本にする」→ 最終確認 → 送信 → 全件照合 → 登録済み
- クラウドの形：`users/{UID}/meta/factory`（status: uploading / complete、uploadId、登録元、件数、プロジェクト名、データの指紋、世代1）、`users/{UID}/{保存先}/r-{ID}`（id・store・json・hash・uploadId・rev・updatedAt・projectId）、大きい記録は `users/{UID}/chunks/{保存先}~r-{ID}~{番号}` に分割
- 送るのは直前の端末内の控えの中身。200件／約4MBずつ。全件を読み直し、内容の指紋（SHA-256）で照合。一致したときだけ status を complete に
- 途中で失敗：status は uploading のまま。同じ端末・同じ中身なら同じ uploadId で続きを送る（上書き＝二重にならない）。中身が変わっていれば新しい uploadId（古い途中の記録は uploadId が違うので使われない。削除はしない）
- 別の端末の uploading や complete のクラウドには登録できない
- 照合用の記録（各記録の指紋）は factory-sync に保存（Sync-3で使う）

### Sync-2-4（実装済み）
- 「この端末へ取り込む」（#/sync-import）：事前チェック（ログイン・接続・owner・クラウドが登録済み）→ クラウドから取り込む内容（件数・名前・内訳・登録元。全件を読み、内容の指紋・件数・全体の指紋を登録時と照合）→ この端末の今のデータ → バックアップ（端末内の控え＋ファイル factory-preimport-YYYYMMDD-HHMM.json＋確認チェック）→「クラウドのデータに切り替える」→ 最終確認 → 取り込み → 全件照合 → 取り込み完了
- 取り込みの直前にクラウドを読み直し、確認画面と同じ指紋か確かめる。バックアップの後に端末が変わっていたら取り込まない
- 置き換えは importAll（全部成功するか、何も変わらないか）。取り込み後に照合し、一致しなければ取り込み前の控えへ自動で戻す
- 端末ごとの記録（master・lastTestRun・lastBackup）とこの端末だけの記録（localOnly）は残す
- クラウドは読むだけ（書き込み・削除なし）。照合用の記録は factory-sync に保存（Sync-3で使う）
- 初回正本の端末で開くと「クラウドと同じ（取り込み不要）」と表示し、取り込みボタンを出さない

## Sync-3：PC・iPhoneの双方向同期（明示ボタン式）— 2026-10-06 実装（3-0〜3-4）
### 方針
- 最初は「ボタンを押したときだけ」：この端末で編集 →「変更をクラウドへ送る」→ 別の端末で「クラウドの最新を確認」→ 差分を確認 →「最新をこの端末へ反映」
- 自動同期・バックグラウンド同期・削除の同期・競合の自動解決は、Sync-3の実機確認がすべて通ってから
- Sync-2-4「この端末へ取り込む」は、新しい端末の初回セットアップと災害復旧用として残す

### クラウドの形（Sync-2-3の形をそのまま使う。データ本体は移行しない）
- `users/{UID}/meta/factory`：status=complete・uploadId（データセットの番号。Sync-3でも変えない）・counts・total・fingerprint に加え、**syncFormat:3・changeSeq（送るたびに1増える変更番号）・lastUpdatedAt・lastUpdatedBy・lastUpdatedDeviceId**
- `users/{UID}/{保存先}/r-{ID}`：id・store・json・hash・uploadId・rev・updatedAt・projectId に加え、送ったときに **deviceId・deviceLabel・updatedBy・cloudRev（その記録の送信回数）・pushedAt**
- 大きい記録は `users/{UID}/chunks/…` に分割（head の parts の数までをつなぐ）
- 既存の383件は書き換えない。「同期を始める」で、全件の照合（件数・内容の指紋・全体の指紋）とクラウドの全件の控え（端末内 factory-sync）を作ってから、印に syncFormat・changeSeq を足すだけ

### 差分の判定（記録ごと・内容の指紋 SHA-256）
| この端末(L) | 基準(B) | クラウド(C) | 判定 |
|---|---|---|---|
| あり | なし | なし | 未送信（新規。同期を始める前からある記録は「同期前からある記録」として最初チェックなし） |
| あり | なし | あり | 同じ内容なら同期済み／違えば競合 |
| L=B | あり | C≠B | 受け取り待ち（更新） |
| L≠B | あり | C=B | 未送信（変更） |
| L≠B | あり | C≠B | L=Cなら同期済み／違えば競合 |
| なし | あり | C=B | この端末で削除（クラウドには反映しない） |
| なし | あり | C≠B | 競合（この端末で削除・クラウドで変更） |
| なし | なし | あり | 受け取り待ち（新規） |
- 基準（B）は端末内 factory-sync の `sync3` に保存。初回正本の端末は登録時の記録、取り込んだ端末は取り込み時の記録から作る

### 送る（Sync-3-2）
- 送る前に一覧とチェック欄と件数の確認
- Firestoreトランザクション：印の changeSeq と、送る記録のクラウド側の指紋が「確認したとき」のままであることを読んで確かめてから書く。違えば送らない（ほかの端末の新しい変更を上書きしない）
- 書いた後にクラウドを読み直して照合 → 一致したときだけ基準を更新（同期完了）
- 印の counts・total・fingerprint も更新するので、Sync-2-4の取り込み（災害復旧）の照合もそのまま通る

### 受け取る（Sync-3-3）
- 受け取る前に一覧（新規・更新・送った端末）と件数の確認
- 直前にクラウドを読み直し（確認時と同じ内容か）、この端末でも同じ記録が変わっていないか確かめる
- 端末内の控えを自動作成（ファイル保存は不要）→ applySyncedRecords（1回の処理で全部書くか何も変えない。rev・更新日時・更新者は送った端末のまま）→ 照合。一致しなければ控えへ戻す

### 競合（Sync-3-4）
- この端末版・クラウド版（送った端末）・更新日時・更新者・項目ごとの違いを表示
- 「この端末版を採用」（クラウドへ送る）／「クラウド版を採用」（この端末へ反映）／「選んだ内容で統合」（項目ごとに選び、新しい版としてこの端末に保存してから送る）／「この端末の削除を保つ」

### 同期しないもの
- 端末ごとの記録（master・lastTestRun・lastBackup）、この端末だけの記録（localOnly）、ゴミ箱（削除をほかの端末へ反映しないため）

### 本物のFirestoreで未確認のこと
- トランザクション・Security Rules・PC/iPhone間の送受信・競合検出と解決は実機確認済み
- 未確認：1回に多数の大きい記録を送る場合の上限（書き込み500件・約10MB）
- 未確認：「この端末で削除・クラウドで変更」の競合で「この端末の削除を保つ」を選ぶケース

## Sync-4a：半自動のお知らせ — v0.10.0（実装済み・実機確認待ち）
### 目的
同期そのものは自動化せず、「未送信」と「受け取り待ち」に気付きやすくする。

### 判定
- 未送信：この端末のローカル記録とSync-3の基準を比べて端末内だけで数える。クラウドには接続しない
- 受け取り待ち：クラウドの記録本文は読まず、users/{uid}/meta/factory の印1件（changeSeq・uploadId・最終更新情報）だけを読む
- metaのchangeSeqと、この端末が前回そろえたときの番号を比較する
- 「クラウドの最新を確認」を押しただけでは消さず、実際に受け取るか競合解決したときに端末側のnotice状態を更新する

### 読むタイミング
- Factoryを開いたとき
- オフラインからオンラインに戻ったとき
- 画面に戻ってきたとき（前回から10分以上たっている場合）
- 同期を始めていない端末、オフライン、未ログイン、お知らせオフではクラウドに接続しない

### 表示
- ホーム：注意があれば帯。何もなければ小さく「☁ 同期：そろっています」
- 同期画面：注意の帯と、この端末だけの「同期のお知らせ」オン・オフ
- 帯を押すと同期画面へ移動

### 安全
- 自動送信・自動受信はしない
- 削除の同期はしない
- 競合の自動解決はしない
- お知らせ機能にはFirestoreへの書き込み命令を持たせない

- Sync-4a追加：ブラウザ内3件＋E2E 56件
- PC役とiPhone役で、印1件だけを読むこと・自動で送受信しないこと・オフライン・お知らせオフを確認
